# План: MCP-режим tgcli

Статус: реалізація та автоматичні перевірки в робочому дереві; повне інтеграційне приймання ще не завершене. Дата: 2026-09-08.

Поточна поведінка, команди й матриця перевірок: [MCP.md](MCP.md). Цей документ зберігає критерії приймання; він не оголошує фічу релізною або всі клієнти перевіреними.

## Результат

```bash
tgcli mcp
tgcli mcp install claude
tgcli mcp install codex
tgcli mcp install copilot
```

`tgcli mcp` запускає локальний MCP-сервер через stdin/stdout. Команди `install` реєструють сервер з іменем `tgcli` у відповідному клієнті на цій машині для поточного користувача, для всіх його проєктів.

Уточнений користувачем обсяг: `claude` охоплює **Claude Desktop і Claude Code CLI**, `codex` — **Codex CLI і Codex Desktop**, `copilot` — **усі локальні інтеграції GitHub Copilot з підтримкою MCP**. Одна команда встановлює інтеграцію в усі знайдені клієнти відповідної родини; додаткові команди для Desktop чи IDE не потрібні. Інсталятор налаштовує вже встановлені застосунки та розширення; встановлення самих клієнтів до задачі не входить.

Для Copilot обов'язкова матриця охоплює CLI, VS Code (Stable та Insiders), Visual Studio, JetBrains IDEs (зокрема Rider), Xcode й Eclipse. «Усюди» тут означає локальну машину згідно з початковою вимогою: GitHub.com, хмарні агенти, браузерні та мобільні клієнти не можуть запускати її локальний stdio-процес. Віддалені SSH/WSL/container hosts мають власний executable, сесію й конфігурацію; локальне встановлення не повинно записувати в них непридатні шляхи.

## Контракт команд

- `tgcli mcp [--session <directory>] [--lock-timeout <seconds>] [--no-wait]`: stdio-сервер без банерів, інтерактивних запитів і звичайного CLI-виводу в stdout. Усі журнали й діагностика йдуть у stderr.
- `tgcli mcp install <claude|codex|copilot> [--session <directory>]`: реєстрація абсолютного шляху до виконуваного tgcli та аргументів `mcp --session <absolute-directory>`. Якщо `--session` не задано, зафіксувати стандартний шлях через наявний механізм tgcli.
- `tgcli mcp --help` і `tgcli mcp install --help`: звичайна довідка без запуску сервера, Telegram чи інсталятора.
- Спочатку виявити всі локальні клієнти родини та їхні профілі, потім налаштувати кожну унікальну конфігурацію. Відсутність CLI у PATH не повинна блокувати встановлення в Desktop або IDE.
- Результат для кожного клієнта/профілю: `installed`, `already-installed`, `not-installed`, `unsupported` або `failed`, шлях конфігурації та конкретна причина. Спільний запис показати як такий, що охоплює кілька клієнтів, без дублювання запису.
- Код завершення 0: налаштовано або вже налаштовано щонайменше один клієнт і немає помилок серед знайдених клієнтів. Відсутні застосунки не є помилкою. Невідома родина, жодного знайденого клієнта, непідтримуваний знайдений клієнт або часткова невдача — ненульовий код; незалежні інсталяції завершити й явно показати частковий результат.
- Успішна інсталяція: назви охоплених клієнтів, ім'я сервера, збережена команда та спосіб перевірити підключення/перезавантажити конфігурацію. Встановлення конфігурації не означає, що Telegram вже авторизований. Не перезапускати IDE/Desktop автоматично й не змінювати їхні налаштування довіри.

## Версія MCP та сумісність

Базова специфікація — **MCP `2026-07-28`**, перевірено 2026-09-08. Попередній варіант плану помилково вимагав `initialize` для всіх клієнтів; це виправлено. Серпневий [roadmap](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/) описує майбутні зміни й не замінює опубліковану специфікацію.

Новий протокол не потребує handshake навіть через stdio. Сервер реалізує `server/discover`, але клієнт може одразу викликати `tools/list` або `tools/call`; кожен запит містить версію та capabilities у `_meta`. Не переносити capabilities з попереднього запиту. Непідтримувана версія повертає `UnsupportedProtocolVersionError` (`-32022`) з переліком підтримуваних версій. Джерела: [базовий протокол](https://modelcontextprotocol.io/specification/2026-07-28/basic), [версії та сумісність](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning).

Для клієнтів старої версії потрібна підтримка обох поколінь протоколу: сучасні запити обробляти з per-request metadata; старий `initialize` / `notifications/initialized` залишити лише в compatibility path SDK. Обов'язкова тестова база — `2026-07-28` та `2025-11-25`; старіші ревізії включати в перевірену матрицю, якщо їх реально використовує потрібний клієнт і підтримує SDK. Не припускати, що встановлена версія Claude/Codex/Copilot вже підтримує нову ревізію. Для кожного клієнта зафіксувати також фактичну версію MCP.

| Зміна | Рішення для tgcli |
|---|---|
| Обов'язковий `resultType` | Звичайні сучасні результати мають `resultType: "complete"`; SDK серіалізує поля відповідно до версії клієнта. |
| Кешування каталогу | Стабільне сортування tools за іменем; сучасний `tools/list` містить `ttlMs` і `cacheScope`. Для першої версії обрати `ttlMs: 300000`, `cacheScope: "private"`. Каталог не залежить від login чи попередніх викликів. |
| JSON Schema 2020-12 | Явні `inputSchema` і `outputSchema`, перевірка фактичного `structuredContent`. Новий MCP дозволяє будь-яке JSON-значення; tgcli свідомо зберігає object DTO та текстову JSON-копію для сумісності. |
| MRTR | Додатковий ввід тепер передається через `InputRequiredResult`, а не серверний JSON-RPC request. Поточні tools не потребують такого вводу; не додавати elicitation/login у першій версії. |
| Extensions і Tasks | Не оголошувати непідтримувані extensions. Для майбутніх фонових операцій використовувати `io.modelcontextprotocol/tasks`, а не старий experimental Tasks API. |
| Deprecated Roots/Sampling/Logging | Не додавати ці можливості. Шляхи передавати явно, журнали писати в stderr. Не використовувати сучасний `ping` або `logging/setLevel`, які прибрано з нового протоколу. |

Поля результатів і схем: [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools). MRTR, extensions, вилучені та deprecated можливості: [офіційний changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog). У tgcli каталог статичний, тому не оголошувати `listChanged` і не будувати непотрібні підписки на його зміни.

Для stdio залишаються UTF-8 JSON-RPC повідомлення по одному на рядок, stdout лише для MCP, stderr для журналів. Скасування — `notifications/cancelled` за request ID; після обробленого скасування більше не надсилати повідомлення цього запиту. EOF завершує процес. Новий протокол забороняє серверні JSON-RPC requests; це перевірити окремо від дозволених responses/notifications. Джерело: [stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio).

Stateless MCP не скасовує стан Telegram. Один довгоживучий `TelegramSession` є внутрішнім ресурсом процесу з обліковим записом, заданим через `--session`, а не протокольною MCP-сесією. Усі параметри читання й курсори передавати явно; не запам'ятовувати «поточний чат». Ексклюзивний lock TDLib залишається необхідним.

Зміни Streamable HTTP (відмова від `Mcp-Session-Id`, заголовки `Mcp-Method`/`Mcp-Name`, нові підписки) та OAuth стосуються майбутнього мережевого транспорту. Для цього локального stdio-сервера HTTP-заголовки та OAuth не потрібні. Якщо згодом додаватиметься HTTP, повторно перевірити ці вимоги; нову фічу не будувати на deprecated HTTP+SSE. Джерела: [transport bindings](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [реліз специфікації](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

## Реалізація сервера

Використати офіційний [MCP C# SDK](https://github.com/modelcontextprotocol/csharp-sdk), пакет `ModelContextProtocol` з hosting/DI. Підтримка MCP `2026-07-28` та старих клієнтів заявлена у [SDK 2.0.0](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.0.0); перевірений актуальний stable — [2.2.0](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.2.0). Початкова ціль залежності — точна версія `2.2.0`; перед реалізацією перевірити доступність пакета, .NET 10, stdio compatibility та single-file publish. Оновлення версії потребує повторних protocol tests, а не лише успішної компіляції. HTTP-транспорт і фоновий daemon не потрібні для цієї фічі.

1. У `Program.cs` зареєструвати MCP-команди, перевірити маршрутизацію кореневого `mcp` та вкладеного `mcp install` у ConsoleAppFramework. Додати `McpCommands.cs` і `McpServerHost.cs`.
2. Винести потрібні Telegram-операції з `TgCommands.cs` і `ForumTopics.cs` у сервісний шар, що приймає сесію й cancellation token та повертає DTO. CLI залишає наявні формати виводу, MCP повертає структуровані результати. Повторно використати побудову даних у `Output.cs` / `ExportSchema.cs`, не перехоплювати глобальний `Console.Out` і не запускати CLI-підпроцес на кожен tool call.
3. Додати `McpTools.cs` з явними назвами, описами, схемами аргументів і результатів. SDK обслуговує `server/discover`, per-request metadata, `tools/list`, `tools/call`, cancellation і окремий legacy handshake; відповідність обом поколінням перевіряється на wire-рівні.
4. Ініціалізувати Telegram ліниво: `server/discover`, legacy handshake і каталог інструментів мають працювати без Telegram-мережі та без login. Перший Telegram-виклик, включно з прямим сучасним `tools/call` без discovery, створює одну спільну `TelegramSession`; одночасні перші виклики не створюють кілька клієнтів.
5. Для першої версії виконувати Telegram tool calls послідовно через cancellation-aware gate. Це також захищає спільний `attachment-index.jsonl`, у якого зараз немає координації конкурентних записів. Очікування в черзі та виконання мають кінцеві таймаути; протокольні запити не блокуються цією чергою.
6. Не викликати інтерактивний `LoginAsync` у MCP. За відсутньої авторизації повернути tool error з інструкцією виконати `tgcli login --session <directory>` у терміналі. Невдала ініціалізація звільняє lock і дозволяє наступну спробу.
7. Обробити EOF stdin, скасування та завершення процесу: припинити приймання роботи, завершити/скасувати активні операції та обмежено за часом закрити TDLib. Якщо native-закриття зависло, процес має завершитися до повторного використання БД. Скасування одного запиту не закриває спільну сесію; припинення очікування TDLib-відповіді саме собою не означає скасування native-операції.

## Інструменти першої версії

Пропонований обсяг: читання Telegram, пошук і завантаження вкладень.

| MCP tool | Наявна CLI-операція |
|---|---|
| `chat_list` | `chat list` |
| `chat_resolve` | `chat resolve` |
| `chat_search` | коренева `search`: пошук чатів |
| `chat_messages` | `chat messages` |
| `message_search` | `chat search`: пошук повідомлень і вкладень |
| `message_get` | `message get` |
| `chat_context` | `chat context` |
| `chat_stats` | `chat stats` |
| `forum_topics` | `forum topics` |
| `message_link` | `link message` |
| `attachment_download` | `download` |
| `diagnostics` | `diagnostics` без секретів |

Зберегти релевантні фільтри `query`, `type`, `topic_id`, межі сторінок і семантику TDLib ID. Для MCP передавати 64-бітні ідентифікатори десятковими рядками у схемах і результатах, щоб клієнти JavaScript не втрачали точність; CLI-схеми залишити сумісними.

Спискові результати містять `items`, `next_cursor`, `has_more` і відомості про неповноту. Курсор повинен містити всі потрібні TDLib offsets; якщо операція не підтримує продовження, явно повідомляти обмеження. Ліміт сторінки за замовчуванням — 30, максимум — 100; сервер обмежує також розмір відповіді, не приховуючи обрізання. Для статистики зберегти наявні поля completeness та termination reason. Структуровану відповідь дублювати JSON-текстом у MCP content для сумісності клієнтів.

`attachment_download` приймає явний абсолютний шлях призначення та повертає шлях, метадані й статус; байти вкладення не включати у відповідь. Позначити локальний файловий побічний ефект в описі й анотаціях інструмента. Помилки операцій повертати як MCP tool errors, не завершувати весь сервер через одну помилку. Деталі Telegram-повідомлень і секрети не писати в журнали.

Поза першою версією: bulk export/download, channel metrics/comments, BotFather та надсилання повідомлень, видача bot token, імпорт/експорт session secret, інтерактивний login і виконання `--transcribe-command`. Це явне обмеження запропонованого обсягу MCP, а не зміна доступності наявних CLI-команд.

## Встановлення у клієнти

Додати `McpInstaller.cs` як координатор родини, окремі адаптери виявлення/читання/запису/перевірки для її клієнтів і тестований runner процесів. Використовувати штатний CLI, де він доступний; для Desktop/IDE без відповідної CLI-команди — редагування їхньої підтвердженої конфігурації. Сам факт запуску `claude`, `codex` або `copilot mcp add` не є доказом охоплення всієї родини.

| Ціль | Штатна команда реєстрації | Стандартна конфігурація користувача |
|---|---|---|
| Claude Code | `claude mcp add --transport stdio --scope user tgcli -- <absolute-tgcli> mcp --session <absolute-session>` | `~/.claude.json`, `mcpServers.tgcli` |
| Claude Desktop | Злиття JSON-запису `mcpServers.tgcli` | macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`; Windows: `%APPDATA%\Claude\claude_desktop_config.json` |
| Codex CLI + Desktop | `codex mcp add tgcli -- <absolute-tgcli> mcp --session <absolute-session>`; TOML-адаптер, якщо CLI недоступний | Спільний `~/.codex/config.toml`, `mcp_servers.tgcli`, для одного локального Codex host/config home |
| Copilot CLI | `copilot mcp add tgcli -- <absolute-tgcli> mcp --session <absolute-session>` | `~/.copilot/mcp-config.json`, `mcpServers.tgcli` |
| Copilot у VS Code | `code --add-mcp <json>` / `code-insiders --add-mcp <json>` або адаптер профілю | User/profile `mcp.json`, `servers.tgcli`; JSON містить `name`, `command`, `args` |
| Copilot у Visual Studio | Адаптер user MCP-конфігурації | Формат `servers.tgcli`; шлях і scope перевірити для підтримуваних версій |
| Copilot у JetBrains IDEs | Адаптер Copilot MCP-конфігурації відповідної версії plugin/agent runtime | Перевірити окремий `mcp.json` або спільну CLI-конфігурацію; не припускати, що всі версії використовують той самий файл |
| Copilot у Xcode | Адаптер конфігурації розширення GitHub Copilot for Xcode | `mcp.json`, формат `servers.tgcli`; фактичний user path визначає адаптер |
| Copilot у Eclipse | Адаптер MCP Server Configurations розширення | Підтверджене сховище preferences відповідної версії; формат `servers.tgcli` |

Формати й команди підтверджені офіційною документацією: [Claude Code](https://code.claude.com/docs/en/mcp), [Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli), [GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers). Стандартні шляхи наведено для пояснення; штатні CLI мають успадковувати середовище користувача й підтримувані ними перевизначення config home.

Окремі Desktop/IDE інтеграції описані в [MCP: Claude Desktop](https://modelcontextprotocol.io/docs/develop/connect-local-servers), [VS Code MCP](https://code.visualstudio.com/docs/agent-customization/mcp-servers), [GitHub Copilot MCP в IDE](https://docs.github.com/en/copilot/how-tos/provide-context/use-mcp-in-your-ide/extend-copilot-chat-with-mcp) і [Visual Studio MCP](https://learn.microsoft.com/en-us/visualstudio/ide/mcp-servers). Для VS Code використовувати актуальну документацію VS Code щодо profile `mcp.json`, оскільки GitHub також наводить старі приклади через `settings.json`.

Перед написанням IDE-адаптерів завершити compatibility spike: перевірити точні шляхи, scope, формати, мінімальні версії, спосіб виявлення розширення та безінтерактивного запису для кожного рядка матриці. Загальна документація GitHub підтверджує MCP в цих IDE, але не встановлює всі фізичні шляхи сховищ. Підтвердити їх документацією/кодом відповідного клієнта та тестовим профілем; не вгадувати шляхи. Відсутній адаптер для підтримуваної інтеграції — незавершена частина фічі, а не підстава оголосити «Copilot everywhere» готовим.

- Виявляти встановлення за executable/app metadata та профілями, для IDE — також наявність Copilot-розширення. Обробляти всі знайдені локальні профілі/канали з Copilot; не створювати профілі для відсутніх клієнтів. Конфігурацію з user scope використовувати для всіх проєктів; якщо конкретна версія має лише workspace scope, явно відобразити це обмеження, не сканувати й не змінювати довільні репозиторії.
- Нормалізувати шляхи конфігурацій і дедуплікувати спільні сховища. Для Codex з єдиним config home достатньо одного запису для CLI/Desktop; різні підтверджені локальні config homes обробляти окремо. Desktop-only сценарій не має вимагати встановлення CLI.
- Файлові адаптери змінюють лише запис `tgcli`: зберегти інші ключі, невідомі поля й коментарі JSONC/TOML, зробити приватний backup та атомарну заміну. Перед заміною перевірити, чи оригінал не змінився паралельно; при конфлікті повторно прочитати/перерахувати зміну або повернути помилку. Пошкоджений документ не перезаписувати порожнім. Не друкувати повний вміст профілю в логах.

- Знайти виконуваний файл цільового клієнта, перевірити підтримку потрібних MCP-команд. Запускати з масивом аргументів, без конкатенації shell-команди. Окремо перевірити Windows `.cmd`/`.exe` launcher-и й пробіли в шляхах.
- Перед зміною прочитати наявний запис через можливості клієнта або файловий адаптер. Однакові command/args — успішний no-op. Інший сервер або інші аргументи під іменем `tgcli` — пояснити конфлікт без перезапису та показати спосіб видалення запису відповідним клієнтом. Не вважати помилку читання доказом відсутності запису.
- Для кожної підтримуваної версії перевірити формат `mcp get/list`; віддавати перевагу JSON, де він доступний. Якщо надійно визначити стан неможливо, завершитися з поясненням несумісної версії до зміни конфігурації.
- Після `add` або файлового запису повторно прочитати збережену конфігурацію й перевірити ім'я, stdio transport, executable і args. Повідомляти успіх лише після перевірки; не видаляти сторонні записи та не скидати налаштування клієнта. Перевірку збереження відокремити від runtime smoke test у самому клієнті.
- У конфігурацію не копіювати session secret, API hash чи телефон. Для встановлення не відкривати Telegram і не брати session lock.
- Визначати абсолютний executable коректно і для опублікованого single-file binary, і для запуску `dotnet tgcli.dll` (пара `dotnet` + абсолютний шлях DLL). Не зберігати `dotnet run` або залежність від поточного робочого каталогу.
- Обмежити час роботи дочірніх процесів і повертати змістовну помилку з їхнього stderr. Після timeout перевірити, чи запис уже збережений, перш ніж пропонувати повторну інсталяцію.

## Спільна сесія між процесами

Один MCP-процес утримує поточний session lock після першого Telegram-виклику до завершення. Інший CLI/MCP-процес з тією самою сесією чекає в межах `--lock-timeout` або отримує помилку з `--no-wait`. Не прибирати lock і не клонувати авторизаційну БД.

Одночасна реєстрація в усіх клієнтах трьох родин підтримується; одночасне використання ними однієї БД потребуватиме окремої реалізації daemon/IPC з [PARALLELISM.md](PARALLELISM.md). Спільний конфіг Codex CLI/Desktop не означає спільний MCP-процес. Для цієї версії користувач завершує активний MCP-процес перед переходом до іншого клієнта або використовує окремо авторизовані сесії. Перевірити й задокументувати цей сценарій також для одночасно відкритих Desktop, CLI та кількох IDE.

## Етапи та критерії приймання

1. **Сервісний шар:** винести операції для зазначеного каталогу; зберегти наявні CLI-параметри та формати. Додати регресійні перевірки спільних CLI/MCP результатів.
2. **MCP runtime:** реалізувати хост, каталог, результати, lifecycle Telegram-сесії, чергу й cancellation. Process-level тести з fake Telegram backend без реального акаунта: сучасний discover → list → call → EOF; прямий сучасний list/call без discovery; legacy initialize → initialized → list → call → EOF. Додати raw JSON-RPC fixtures / застосовні офіційні conformance scenarios, щоб спільна помилка SDK-клієнта і сервера не маскувала порушення протоколу.
3. **Інсталятори:** завершити compatibility spike для всієї Desktop/CLI/IDE-матриці, потім перевірити всі адаптери на fake executable-ах і тимчасових профілях: перша інсталяція, повторна, конфлікт, відсутній/старий клієнт, невдала реєстрація, timeout, помилка читання, persisted-value verification, сторонні записи, config-home overrides, Unicode та пробіли в шляхах. Додати Desktop без CLI, CLI без Desktop, обидва разом, кілька IDE/профілів/каналів, спільне сховище, частковий збій, невідомий формат, JSONC/TOML-коментарі, конкурентну зміну та атомарність файлового запису.
4. **Помилки та ресурси:** перевірити відсутній login, зайняту БД, збій ініціалізації, одночасні перші виклики, скасування в черзі й під час виконання, EOF, завершення з активним запитом, звільнення lock. Перевірити, що stdout містить лише MCP-повідомлення, а Telegram-помилка не руйнує наступний запит.
5. **Контракт даних й протоколу:** перевірити курсори без пропусків/дублів, topic filters, межі обсягу, completeness, 64-бітні ID поза безпечним діапазоном JavaScript, коректні посилання й завантаження файлу. Перевірити per-request version/capabilities без успадкування між викликами, відхилення непідтримуваної версії до Telegram-операції, `resultType`, cache hints і стабільність tools/list, JSON Schema 2020-12, version-gated legacy результати, відсутність серверних requests та повідомлень після скасування. Protocol errors відокремити від `isError` результатів виконання tools.
6. **Збірка й інтеграція:** `dotnet test TgCli.Tests/TgCli.Tests.csproj`; publish-матриця `linux-x64`, `osx-x64`, `win-x64`; E2E саме опублікованого binary з modern/legacy wire protocol, fake native CLI, ізольованими Desktop/IDE-профілями, persisted-value verification, backup, повторною інсталяцією та запуском із записаного конфігу. Окремий workflow запускає її для pull request і main, release workflow — перед пакуванням. У реальних Claude Desktop і CLI, Codex Desktop і CLI та кожній Copilot-інтеграції матриці ще перевірити реєстрацію, список tools та один Telegram read call на відповідній ОС; зафіксувати перевірені версії клієнтів/розширень. Спільний файл не замінює перевірки обох застосунків. Автоматичні тести не змінюють справжні профілі користувача.
7. **Документація після реалізації:** оновити README з робочими командами й повною матрицею Desktop/CLI/IDE, ОС і перевірених версій, правилами автовиявлення, результатами часткової інсталяції, авторизацією, параметром `--session`, перевіркою/видаленням інтеграції та troubleshooting; створити `MCP.md` з каталогом tools і прикладами схем. Оновити `PARALLELISM.md`, обидва проєктні agent skill-файли та CHANGELOG. Перевести цей план у завершений статус лише після перевірок; номер релізу узгодити з фактичним релізом.

Фіча готова, коли всі чотири запитані команди працюють, кожна команда `install` охоплює всі знайдені підтримувані клієнти своєї родини, повторне встановлення не створює дублів, кожен клієнт обов'язкової матриці бачить і викликає Telegram tools, існуючий CLI проходить регресійні перевірки, а документація описує реалізовану поведінку й обмеження. Обов'язкові wire/conformance перевірки MCP `2026-07-28` і legacy compatibility та матриця фактичних версій MCP клієнтів; сама залежність від нового SDK не доводить сумісність. Реалізація лише трьох CLI-адаптерів не задовольняє цей план.
