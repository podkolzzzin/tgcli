## Findings, highest impact first

### MCP tool inventory (additional to the 31 CLI surfaces)

Source: [McpTools.cs](../../../McpTools.cs#L51), [backend defaults](../../../McpTelegramBackend.cs#L18). All 12 tools accept `request_timeout` integer 1–300, default 60 seconds (includes queue time). Unknown properties are rejected. Required IDs below are nonzero signed 64-bit decimal **strings**; topic IDs are integers. Every tool has explicit input/output schema. Successful responses include structured content and a text copy; tool failures use `isError`. The server targets a 512 KiB successful response limit. No live Telegram tool was invoked during this audit.

Page cursors are opaque and bound to operation/filter fingerprints. This is intentionally different from CLI raw message offsets. MCP does not expose bot operations, login/session secrets, bulk export, batch downloads or transcription; these omissions are deliberate capability boundaries, not missing implementation parity.

1. **P1: `bot write` can send to a human account before rejecting it as not a bot.** `Write` obtains a private chat (`BotCommands.cs:155-156`) and sends text / executes a click (`159-170`) before `ResolveBotUserAsync` is called while constructing the response (`176`). `ResolveBotChatAsync` only checks `ChatTypePrivate` (`191-200`); `UserTypeBot` is checked at `209-212`. Thus a valid human username with `--text` has a side effect before the advertised bot-only contract is enforced. Evidence is static, not a live send. Verify bot identity and all arguments before mutation, with a fake-backend regression case asserting no SendMessage occurs.

2. **P1: invalid output format can be rejected after bot mutations.** `bot create`, `remove`, `token --revoke`, and `write` only validate `format` in `PrintObject` (`BotCommands.cs:476-493`), after creating/deleting/rotating/sending/clicking (`23-28`, `61-76`, `113-121`, `159-170`). A typo can perform the requested action and then exit 1 with no result, making retry hazardous. Validate supported formats at entry. Same late-validation pattern on many reads incurs unnecessary login/network delay, but bot mutations are the material consequence.

3. **P2: unknown command reports success.** Installed binary `tgcli no-such-command` exits 0, writes root help to stdout, and leaves stderr empty. Bare `chat messages`, `transcribe`, and `mcp install` also exit 0/help despite required arguments; this can be intentional help-on-empty UX, whereas a typo is a clear automation ambiguity. Typed errors (`--chat-id not-an-integer` or overflow) correctly exit 1 with empty stdout and a concise stderr parse error. Evidence: [CLI probes](evidence/cli-probes.jsonl); routing is `Program.cs:14-29`. Add subprocess CLI contract cases for unknown commands, missing required options with nonempty arguments, bad options/types, and help.

4. **P2: chat enumeration can silently output nothing for accepted formats.** `Output.ParseFormat` accepts `json`, `plain` and `text` (`Output.cs:69-79`), but `PrintChats` handles only TSV/JSONL/Markdown and has no default (`195-237`). `search`, `chat list` and `chat resolve` can fetch real rows and return success with empty output for those formats. Existing help advertises only supported TSV/JSONL/MD, but accepting other valid global formats silently is still inconsistent. Reject unsupported formats before reading or implement them.

5. **P2: bot result statuses do not establish success.** Creation returns `status=unknown` / null token if any reply lacks a token (`BotCommands.cs:29-41`); token/revoke returns null token plus `revoked=true` based solely on input (`121-133`); delete always returns `status=requested` (`76-86`). All exit normally. Replies are selected as the newest nonoutgoing user message after a cursor without validating expected prompt/reply content (`232-249`). `bot write` fetches history immediately after send/callback (`173`), with no wait for a fresh bot response. Report these as workflow limitations; no destructive tests were performed. No BotCommands test class or CLI bot workflow coverage found.

6. **P2: documented lock controls are not universally exposed.** README.md:181 tells session-backed commands to use `--lock-timeout` / `--no-wait`; the installed command inventory offers these only on diagnostics, chat messages/search/stats, forum topics and mcp. Export/download/message/link/login/bot/list/resolve cannot accept the suggested flags. Several new leaf flags also have no help descriptions (channel selectors/formats/dates, export resume/incremental/integrity options, stats/context and lock/request timeouts). Group `chat --help`, `bot --help`, etc. return the complete root command list rather than scoped help; `mcp --help` shows the server flags but omits its install subcommand.

## Stdout, stderr and exit behavior

- All captured help/version calls: exit 0, help/version on stdout, stderr empty.
- `Program.cs:15` routes framework parse errors to stderr. `FriendlyErrorFilter` (`32-65`) catches cancellation => exit 130 + `Operation canceled.` on stderr; other exceptions => exit 1 + message only, recursively unwrapping single aggregate/reflection wrappers. It does not emit a stable JSON error envelope or categorized failure codes.
- Safe pre-session probes confirmed invalid transcribe format, invalid batch parallelism 0/33, invalid batch format, bot remove without `--confirm`, and channel comments without `--post-id`/`--all` all exit 1 with empty stdout and readable stderr. No authorization or session opening happened for these probes.
- `download-batch` writes an ordered result for every request, including individual failures, to stdout and then throws when any failed (`TgCommands.cs:204-230`). Consumers must check exit status as well as per-row `ok`/`error`; partial output is intentional.
- `chat export` always writes a JSON manifest to stderr before output formatting/serialization (`TgCommands.cs:1191-1204`). File output writes `<output>.manifest.json` after writing data (`1250-1263`); success is otherwise quiet. Stderr is therefore diagnostics/manifest/error mixed, not error-only or one stable machine-readable stream.
- Session export prints an authorization secret; session import consumes stdin and has no success payload (`SessionSecret.cs:14-28`). No such secrets were read in this audit.
- Installer output is human-oriented status lines plus prose (`McpCommands.cs:18-26`), not JSON/JSONL; a detected failure/unsupported client or no successful target returns exit 1. MCP stdout is its separate protocol stream.

## Data/schema/date/ID contract

- `chat list`/`resolve`/top-level `search` JSONL uses unversioned `ChatRow`: `chat_id,title,type,username,unread,last_message` (`Output.cs:19-31`). TSV has a header; tab/newline values are flattened.
- Simple messages are unversioned `MessageRow` (`Output.cs:33-60`): numeric `chat_id,message_id`, local `date`, sender ID/name, kind/file ID/text/reply ID, query and optional origin/link fields. Formats differ in ordering: JSON/JSONL/Markdown preserve ascending message IDs; plain/TSV explicitly sort descending (`Output.cs:118-123`, `240-337`). Export rich JSON/JSONL sorts date then message ID (`140`); migrated simple outputs sort by message ID, not global date.
- Rich JSON and JSONL both use `schema="tgcli.message"`, `schema_version="5.0"` (`ExportSchema.cs:9-10`). Root fields: `chat_id,message_id,short_message_id,tg_url,source_chat_id,date,edit_date,sender_type,sender_user_id,sender_chat_id,sender_display_name,sender_username,kind,text,entities,reply_to_chat_id,reply_to_message_id,reply_target,forward_origin,interaction_info,view_count,forward_count,reply_count,reaction_counts,paid_reaction_count,has_comments,poll,service_event,attachments,is_deleted,tombstone,links` (`38-80`). Tombstones have a smaller schema (`83-90`). `--fields` preserves schema/name and rejects unknown fields after rows are fetched (`Output.cs:177-192`); non-JSON formats do not project fields.
- Rich dates, bot message dates and channel/comment dates are UTC ISO-8601 roundtrip with an explicit offset (`ExportSchema.cs:250-251`, `BotCommands.cs:366`, `TgCommands.cs:725,836`). Simple message dates use machine-local time without offset (`Output.cs:370`). `message get --format tsv` uses culture-dependent `DateTimeOffset.ToString()` through string.Join (`TgCommands.cs:517`). Input date filters parse invariant-culture DateTimeOffset, but absent offsets still depend on local time (`1176-1178`, `892-893`). Prefer explicit offsets for reproducibility.
- `message_id` is TDLib's signed 64-bit ID and only unique with `chat_id`; `short_message_id = message_id >> 20` (`ExportSupport.cs:173`, README.md:171-174). `channel comments --post-id` and metrics from/to post IDs are short/public IDs, unlike message/get/link/download/context IDs. Installed help does not explain that distinction on channel flags. `topic_id` is a 32-bit forum topic ID. CLI JSON writes IDs as JSON numbers; MCP uses decimal strings, a separate contract.
- Transcription JSON/jsonl is one transcript object, not one segment per line; plain/text is transcript text (`TranscriptionCommands.cs:14-28`). JSONL aliases JSON for singleton outputs such as diagnostics, status, message get, links, stats and migrations. Chat search with `--queries` prints separately per query (`TgCommands.cs:1105-1129`), so `--format json` produces multiple independent arrays, not one JSON document; TSV repeats headers. Output query attribution exists in simple message schema.
